# Internationalization (i18n)

Lilo ships English and French. There are two small, dependency-free translation layers:

| Layer | Drives | Source of truth | Follows |
|-------|--------|-----------------|---------|
| **Web chrome** (Svelte UI) | tabs, sidebar, command bar, settings, panels | `lilo-ui/src/lib/i18n/locales/*.json` | the in-app **Language** selector (Settings > General), instantly |
| **Native** (AppKit) | menu bar, native dialogs | `lilo-ui/src/lib/i18n/locales/*.json` (`native` namespace) | the same in-app choice, else the macOS system language - applied on next launch |

Both layers translate from the same JSON catalogs - there is no second place to maintain.

One selector drives everything: the web chrome switches instantly; native menus/dialogs pick up the choice on the next launch (the menu bar is built once at startup). When no choice has been made, native falls back to the system language.

## Web UI

Call `t()` with a dotted `namespace.key`:

```svelte
<script lang="ts">
  import { t } from "../lib/i18n/state.svelte";
</script>

<button aria-label={t("findBar.closeFindBar")}>×</button>
<span>{t("downloadIndicator.downloadsCount", { count })}</span>
```

- `t(key, params?)` resolves the active locale, falls back to English, then to the key itself (so a missing string is visible, never blank).
- Placeholders are `{name}` style, filled from `params`.
- A numeric `count` is digit-grouped for the locale, and picks a plural form when the key holds one per [plural category](https://cldr.unicode.org/index/cldr-spec/plural-rules) instead of a string: `"pagesImported": { "one": "{count} page imported.", "other": "{count} pages imported." }`. A category the catalog lacks (French `many`) falls back to `other`.
- `t()` reads a reactive rune, so changing the language updates every label instantly - no reload.

**Architecture** (`lilo-ui/src/lib/i18n/`):

- `translate.ts` - pure resolver; English is imported up front, other catalogs load on demand (`loadCatalog`). Unit-tested (`translate.test.ts`).
- `state.svelte.ts` - the reactive current-locale rune + `t()`. (Runes live here so plain `.ts` files, and the unit tests that run them under `tsx`, never import them.)
- `locales/en.json`, `locales/fr.json` - message catalogs, namespaced by feature.

The default locale comes from `navigator.language`; the Settings selector persists an override via the `locale` setting and applies it on load.

### Add or change a string

1. Add the key under the right namespace in **both** `en.json` and `fr.json`.
2. Use `t("namespace.key")` in the component.

`translate.test.ts` fails `make ui-test` (and CI) if `en.json` and `fr.json` ever drift apart, so every key must exist in both.

> A pure `.ts` model that needs translation should expose catalog **keys** (e.g. `labelKey`) and let the Svelte consumer call `t(key)` - see `settingsPanelModel.ts`. This keeps the model importable by the `tsx` unit tests, which can't load Svelte runes.

### Add a language

1. Add `locales/<code>.json` with the same keys as `en.json`.
2. Register it in `translate.ts`: extend the `Locale` type, `SUPPORTED_LOCALES`, and `loadCatalog`.
3. Cover it in the key-parity test in `translate.test.ts`, which compares `en` and `fr` only.
4. For native menus and dialogs, teach `scripts/generate_native_strings.py` and `Lilo/App/Localization.swift` the new code; both handle French only, so native surfaces otherwise stay English.

## Native (AppKit)

The English string is the key:

```swift
menu.addItem(withTitle: "New Tab".localized, action: ...)
```

`String.localized` returns the French value when the active native locale is French - the in-app language choice (persisted to `UserDefaults` when the selector changes), or the system language as a fallback - and the original English otherwise. Strings absent from the table stay English, so wrapping a string is always safe. Interpolated strings use `String(format: "Install %@?".localized, name)`.

The translations live in the **`native` namespace of the shared catalogs** (`en.json`/`fr.json`), keyed by the English string. `make ui-build` runs `scripts/generate_native_strings.py`, which compiles that namespace into `Lilo/Generated/NativeStrings.swift` (generated, gitignored - same pattern as the embedded UI bundle).

To translate a native string: wrap it in `.localized`, add an `"English": "Français"` row under `native` in `en.json` (identity) and `fr.json` (translation), then `make ui-build`.

`nativeStrings.test.ts` (run by `make ui-test`) scans `Lilo/` for literals that reach `.localized`, directly, through a ternary or through a localizing helper, and lists any without a row in both catalogs. Localize a literal where it is written, not after it went through a dictionary or a variable, so the scan sees it.

## Commands

```bash
make ui-test     # runs the i18n unit tests + the en/fr parity check
make ui-lint     # type-checks every t() call site
```
